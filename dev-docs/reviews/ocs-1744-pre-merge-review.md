## MPC / consensus

### `mpc-consensus-1` — Orchestrator computation slot leaks / node aborts when `compute()` panics
- **Severity: HIGH (verified real).** MUST-FIX-BEFORE-MERGE.
- **STATUS (2026-06-26): ✅ FIXED** (`ff3feba0f6`) — `compute()` is wrapped in `compute_catching_panic` (`catch_unwind(AssertUnwindSafe(..))`), a `ComputationCompletionUpdate` is always sent so the core slot is reclaimed on the panic path, and two unit tests guard it (`panic_in_compute_becomes_a_failed_result`, `ordinary_failure_passes_through`).
- **File:** `crates/ika-core/src/dwallet_mpc/crytographic_computation/orchestrator.rs:323-360`
- **Mechanism (plain terms):** The core slot is reserved unconditionally at line 356 (`currently_running_cryptographic_computations.insert(...)`) and is only ever reclaimed when a `ComputationCompletionUpdate` is read back. That update is sent *inside* the rayon closure, only after `computation_request.compute(...)` (line 329) **returns normally**. If `compute()` panics, the closure unwinds, the `handle.spawn` send at line 339 is never reached, and the completion update is never produced. Under `[profile.release] panic='abort'` the panic kills the whole validator; under test/simulator (`panic='unwind'`) the rayon `panic_handler` only logs and the worker survives, so the slot is leaked for the rest of the epoch. Accumulated leaked slots drive `has_available_cores_to_perform_computation()` permanently false → epoch MPC wedges silently. The branch diff added only the `max_computation_cores` cap (lines 110-115); the panic guard is absent.
- **Reachability:** `compute()` dispatches into external 2PC-MPC / class-groups `advance()` on inputs aggregated from other (possibly malicious) parties, and the in-tree dispatch itself contains `unreachable!()`/unwrap sites (e.g. `sign.rs`). The orchestrator has zero resilience to *any* panic in `compute()` — independent of the (unproven) remote-trigger hypothesis. The authors' own msim-path comment (lines 289-298) acknowledges a rayon-worker panic aborts the process.
- **Suggested fix:** Wrap the `compute()` call in `std::panic::catch_unwind(AssertUnwindSafe(...))`, convert a caught panic into a failed `computation_result` (so identified-abort/error handling can run), and **always** send a `ComputationCompletionUpdate` on both the success and panic paths so the slot is reclaimed unconditionally. Equivalently, guard the slot with an RAII/`Drop` token that removes it from `currently_running_cryptographic_computations` if the closure unwinds. Add a unit test that forces a panic inside `compute()` and asserts the slot is released and a completion update is delivered (per CLAUDE.md test-test-meaningful-features: inject the fault, confirm the slot-release evidence, revert).

### `ocs-verifier-core-1` — `verified_objects` zip-truncates a relay-controlled short results vec, returning a partial set as `Ok`
- **Severity: LOW (verified real; downgraded from HIGH).** Recommended before merge — one-line fix.
- **File:** `crates/ika-core/src/sui_connector/verified_reader.rs:284`
- **Mechanism (plain terms):** `for (id, slot) in ids.iter().zip(resp.results)` — `zip` stops at the shorter iterator. `resp.results` is fully relay-controlled (`SuiMirrorProofProvider.batch_verified_objects`, `client.rs:280`), and **nothing checks `resp.results.len() == ids.len()`**. If a malicious peer omits trailing slots, the loop never visits the missing trailing ids, so the per-slot `None`→`NotFound` guard (line 285) and the id-binding check (line 290) never run for them. The function returns `Ok(out)` with fewer `VerifiedObjects` than requested — violating its own doc contract ("a hole is a failed read"). The serving side (`proof_provider.rs:539-548`) explicitly rejects positional misalignment; the consuming side has no symmetric length check.
- **Why downgraded:** The headline committee-corruption scenario is refuted — `get_epoch_start_system` (`lib.rs:517-535`) re-iterates the BLS-verified `active_committee.members` and `.ok_or_else(InvalidCommittee)?` on any id not found, so a dropped validator hard-errors rather than silently shortening the committee. Residual silent-drop impact exists only on sibling callers lacking a re-find guard (`get_validator_inners` → mpc_data `.get(&id)` yields `None`; `for_each_dynamic_child` consumes a truncated child set). Robustness, not trust violation.
- **Suggested fix:** Before the loop, `if resp.results.len() != ids.len() { return Err(ReaderError::Transport(TransportError::NotFound(...))) }` (or assert every requested id is present). One line, closes the contract gap for every caller at once.

### `ocs-binding-1` — `pending_active_set` ExtendedField child is read UNBOUND (listed, not derived or owner-checked)
- **Severity: LOW (verified real).** Recommended — small fix. _Added 2026-06-26 from the read-path binding review ([`../plans/ocs-read-binding-and-verification.md`](../plans/ocs-read-binding-and-verification.md), Q4)._

### `ocs-transport-1` — Relay `execute_transaction` returns unverified effects bytes (dormant landmine)
- **Severity: LOW (verified real).** Not blocking.
- **File:** `crates/ika-network/src/sui_state_mirror/client.rs:493-537` (contract on `transport.rs:24-34`)
- **Mechanism (plain terms):** `SuiMirrorTransport::execute_transaction` BCS-decodes relay-returned `effects_bcs` and returns them as `SubmittedTransaction.effects` **without verifying against the committed checkpoint**; the only checks are the echoed digest and a bare `get_transaction_checkpoint` pass-through (itself unproven — no inclusion proof, no BLS). A malicious relay could fabricate both the effects and the commit confirmation. The in-source comment (lines 507-520) acknowledges this verbatim.
- **Why safe today:** Every wiring path makes it unreachable — `FallbackTransport` routes `execute_transaction` to direct gRPC; `VerifiedSuiTransport` returns `unreachable`; the node submit client is always the `VerifiedSuiTransport` wrapper (`lib.rs:611-614`). - **Suggested fix:** Either (a) make the hazard fail-closed — have `SuiMirrorTransport::execute_transaction` return an explicit `unreachable`/unsupported error instead of silently returning unverified effects, so a future mis-wire fails loudly rather than trusting forged bytes; or (b) verify the effects against a committee-proven checkpoint before returning. Option (a) is the minimal, surgical guard.

### `network-mirror-1` — `submit_transaction` serving handler has no inflight cap and forwards arbitrary peer tx to the local full node — **FIXED (`550db6ba2f`)**
- **Severity: MEDIUM (verified real).** Not blocking (opt-in serving role).
- **File:** `crates/ika-network/src/sui_state_mirror/mod.rs` `make_server`, `crates/ika-network/build.rs`
- **Mechanism (plain terms):** `make_server` installed `InflightLimitLayer` for the five heavy read RPCs but **not** for `submit_transaction`, which unconditionally called `self.transport.execute_transaction(&tx)` on the validator's own full node for any peer-supplied `Transaction`. The anemo router (`lib.rs:1531-1560`) has no allowed-peers firewall; any discovered/admitted p2p peer could invoke it, with `max_frame_size=1 GB` and `max_concurrent_bidi_streams=500`.
- **Triggering scenario:** A compromised/admitted peer opens many concurrent `submit_transaction` streams of well-formed (garbage) signed tx; each costs a full-node gRPC round-trip + validation, with unbounded concurrency — amplification DoS onto the validator's own full node. Tampered tx are still rejected on-chain and effects are re-verified client-side, so this is availability-only, no safety break.
- **Resolution (scope sharpened):** `submit_transaction` had **no live caller** — writes are notifier-gated and the notifier runs a direct uplink, and `SuiMirrorTransport::execute_transaction` already fail-closes. So instead of capping it, it was **removed entirely** (`.method()` dropped from `build.rs`; handler + `SubmitTransaction{Request,Response}` types deleted). Then *every* served read got an inflight cap — the five that had one plus the seven that didn't (`last_checkpoint_of_epoch`, `get_transaction_checkpoint`, `get_checkpoint_summary_by_digest`, `get_latest_checkpoint`, `get_current_epoch`, `get_reference_gas_price`, `get_chain_identifier`) — via a `macro_rules! inflight` (each `add_layer_for_*` is generic over its own request type). Per-peer rate-limit / admitted-peer firewall deferred; the inflight ceilings bound the DoS.

The server-side `MAX_BAG_PAGE_SIZE`/`MAX_BATCH_OBJECTS`/`MAX_CHANGESET_PAGE` caps only constrain an *honest* server's output. A malicious peer can answer a small request with a ~1 GB frame of bogus entries → ~1 GB alloc + per-entry verification before discard.
- **Why low:** Frame-bounded at 1 GB; `max_frame_size` is a pre-existing global, not introduced here; BLS dedup reduces BLS to O(distinct checkpoints) (dominant cost is the Merkle check + the allocation). Capped amplification, not unbounded DoS.
- **Suggested fix:** In the consumers, reject responses where `resp.entries.len()` (resp. `results.len()`) exceeds the requested `page_size`/`limit` before allocating/verifying. Consider a per-service response-size cap below the 1 GB global for these RPCs.

## OCS ingest / pump (mirrored-node hardening)

### `ocs-ingest-2` — Relay omitting `session_events` bag entries only bumps a metric; the omitted session is never ingested locally
- **Severity: LOW (verified real).** Not blocking.
- **File:** `crates/ika-core/src/sui_connector/bag_event_pump.rs:183-222`
- **Mechanism (plain terms):** `collect_bag` compares accumulated `listed` against the authenticated `Bag.size`; when `detect_omission` (mirrored node) and `listed < expected_size`, it emits `warn!` + increments `bag_omission_suspected_total` but does **not** fail/retry the tick. `advance()` then diffs/broadcasts only the under-served set and commits it to `self.seen`. Per-entry proofs attest authenticity, not membership completeness (the bag parent isn't fetchable). A relay cannot forge the count to hide a session (binding/currency checks reject substitutes), so omission reliably trips the warning — but the response is non-fatal.
- **Why low:** On a mirrored/peer-only node the bag pump is a low-latency live-start optimization; an omitted session is still picked up via the consensus catch-up backstop. The gap is defense-in-depth.
- **Suggested fix:** On *sustained* omission (suspicion persisting across N ticks), escalate — rotate relay/peer and/or surface a fatal-tier alert — rather than logging indefinitely. Low priority.

### `ocs-wiring-1` — `BagEventPump` warns at 20 Hz with no backoff on sustained tick failure
- **Severity: LOW (verified real).** Not blocking. **Shares root with `ocs-ingest-2`** (same loop's failure-response discipline; fix them together).
- **File:** `crates/ika-core/src/sui_connector/bag_event_pump.rs:96-99`
- **Mechanism (plain terms):** `loop { tick.tick().await; if let Err(e) = self.advance().await { warn!(...) } }` at a 50 ms interval with no backoff. On a genuine relay/proof outage, `advance()` errs every tick → ~20 warn lines/sec for the whole outage, drowning logs, with no relay relief. The not-yet-available-coordinator case returns `Ok` (only `debug!`), so it doesn't flood — only real relay/proof errors do. Contrast the executor's `verified_read_retry_backoff` (1s→30s escalation); the pump has none.
- **Suggested fix:** Add exponential backoff + log-severity escalation (and a rate-limit on the warn) on the failure path, mirroring `verified_read_retry_backoff`. Combine with `ocs-ingest-2` into one "pump failure/omission response" change.

## Cache / retention

### `ocs-cache-committee-1` — Verified-cache retain window defeated by clamping `prune_floor` to the never-pruned bootstrap committee summary
- **Severity: MEDIUM (verified real; downgraded from HIGH).** Not blocking, but should be fixed soon for long-running direct validators.
- **File:** `crates/ika-core/src/sui_connector/verified_state_cache.rs:279-288`; `authority_perpetual_tables.rs:422-427`
- **Mechanism (plain terms):** `prune_floor()` computes `floor = head - window`, then `floor = floor.min(*oldest_committee_summary.sequence_number())`. `oldest_sui_committee_summary()` returns the lowest-epoch (bootstrap) summary, whose seq is fixed because that column is never pruned on a schedule (only wiped by format-recovery). Once the chain advances past `bootstrap_seq + window`, the `.min()` pins the effective floor at `bootstrap_seq` forever, so `prune()` never drops anything — the retain window (default 432,000, whose stated purpose at `node.rs:494-498` is to bound the cache) becomes a no-op. This diverges from the sibling `ChangesetIndex::prune` (`ocs_currency.rs:421-435`, plain `head - window`, no clamp) despite the doc claiming it "Mirrors" it. The unit test `prune_floor_never_drops_below_oldest_committee_summary` encodes the leak as intended behavior, so it won't catch it.
- **Why downgraded:** The cache is keyed by `ObjectID`, so growth is bounded by the count of *distinct* Ika object IDs modified at/after the anchor, not by checkpoint count — slow-onset (also gated behind the 432k-checkpoint onset delay), not the per-checkpoint blowup the title implies. The clamp also has a legitimate rationale (a mirrored peer bootstraps from `oldest_summary.seq + 1`).
- **Suggested fix:** Decouple the two concerns: keep the bootstrap-anchor floor only for the mirrored-bootstrap retention path, but use a moving floor (`head - window`) for general pruning — or clamp to a *moving* mirrored-bootstrap floor rather than the immutable epoch-0 anchor. Update the misleading "Mirrors ChangesetIndex" doc, and fix the unit test to assert pruning actually advances once `head - window > bootstrap_seq` (test-test it: confirm a stale-but-post-anchor object is evicted).

## Authority / epoch close

### `authority-epoch-1` — v4 epoch-close gate on `handoff_signatures_meet_quorum` is non-deterministic across honest validators
- **Severity: MEDIUM (verified real; downgraded from HIGH).** Not blocking (backstop-bounded), but the inline comment is provably wrong and should be corrected.
- **File:** `crates/ika-core/src/authority/authority_per_epoch_store.rs:4189` (decision), `3177` (quorum), `4624-4640` (record path)
- **Mechanism (plain terms):** v4 close is gated on `handoff_signatures_meet_quorum()`, which sums weight over the per-epoch `handoff_signatures` table. Rows are written only when `record_handoff_signature` reaches `Recorded`/`Certified` — which requires this validator's `expected_handoff_attestation` to be installed (off-consensus, via the local snapshot/mpc-data-ready path) **and** the consensus-pubkey provider to be loaded (a 5s background Sui poll). Until then, sequenced `EndOfPublishV2` bundles are buffered and write no row. So *whether* each row exists at commit round R depends on off-consensus install timing, not purely on the consensus sequence — exactly the dependency the adjacent EOP apply-arm comment (4624-4638) and `record_handoff_signature`'s doc (2800-2806) cite as the reason the EOP vote is counted *unconditionally*. The inline comment at 4185-4188 ("a deterministic function of the consensus-sequenced handoff_signatures table") is inaccurate. Because checkpoint sequence numbers are assigned by message-accumulation order, a divergent close round yields divergent end-of-epoch checkpoint content/position, which the v4 grace/anchor machinery exists to keep identical.
- **Why downgraded:** Two strong mitigations narrow reachability well below the finding's `#1736`-style framing. (1) Buffered-quorum adoption (2865-2874) lets a lagging validator reach quorum from peer signatures alone, *without* its own snapshot — and because the attestation is spec-deterministic, the buffer crosses quorum at the same sequenced bundle index as a peer's direct path, *provided its provider is loaded*. (2) The active-committee provider depends only on `active_committee` (stable from epoch start), so it installs within the first ~5s poll and stays installed for any continuing validator. A genuine divergent close additionally requires the provider absent at close time (a multi-minute RPC outage spanning the whole grace window, which would hit peers equally) or a tight one-commit interleaving — reachable but uncommon, and self-healed by the `grace*4` liveness backstop.
- **Suggested fix:** First, correct the inaccurate inline comment at 4185-4188 to state plainly that the table's *write order* is consensus-ordered but *whether* a row is written depends on off-consensus attestation/provider install — and that close-determinism rests on the buffered-quorum adoption + `grace*4` backstop, not on the gate being a pure consensus function. Then evaluate whether the close gate should depend only on consensus-deterministic inputs (e.g. the unconditional EOP tally, as the EOP apply-arm does) rather than `handoff_signatures_meet_quorum`. Given the backstop, treat the comment fix as the immediate action and the gate rework as a design-review item before relying on it for fast deterministic close.
